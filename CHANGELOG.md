# Changelog

All notable changes to Echidna are recorded here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Monorepo scaffold: pnpm workspaces with Turborepo, and a Cargo workspace for the Rust crates.
- `@echidna/ui-tokens`: colour palette, light and dark themes, typography with per-locale font fallbacks, spacing and radii, a WCAG contrast utility and generated CSS custom properties.
- Separate fill, label and text tokens for each status colour, so every status pairing meets WCAG AA in both themes.
- `@echidna/core`: shared types for specs with provenance, netlists, layout (devices, boards, layer stacks, slots and rails), rule violations and projects.
- `echidna-solver` and `echidna-solver-wasm` crate stubs.
- README.
- `@echidna/web`: Next.js 16 App Router app with localised routes for English, French, Spanish, Chinese, Japanese and Russian, falling back to English for missing strings.
- Compact language menu and a sun / moon theme toggle, built with shadcn/ui. The theme follows the system until toggled, is remembered per user and applies before first paint.
- Tailwind CSS v4 and shadcn/ui, themed from the Echidna design tokens.
- Studio at `/[locale]/studio`: top bar (project, preset, Learn mode, Simulate), collapsible component library, 3D board view, and a resizable schematic / inspector column clamped to 20–80%.
- Validator drawer: a slim "All checks passed" bar when clean, a peek of the two worst issues with counts, and an expandable full list. Selecting an issue selects its component, and estimate-based fails read "Likely to fail".
- Panel sizes, library collapse, drawer state and Learn mode are remembered per user.
- Home page: a live "Try a swap" demo (5 V supply, series resistor, LED) where changing the resistor recalculates the LED current, animates current flow and LED glow, and updates the pass / warn / fail verdict. Also sections on the three slot checks, the six device types and value provenance, with load and scroll animations that respect reduced motion.
- Studio panels use shadcn/ui building blocks: empty states, search input group, issue list items, severity badges and tooltips on icon buttons. The 3D grid follows the theme.
- Home hero: an isometric 3D development board that assembles itself in a loop. Nine parts (processor, memory, capacitors, resistors, USB-C, inductor, crystal, LED and pin header) drop into place one by one, each highlighted in orange with a label as it lands, then the board powers up, its traces glow and the LED lights before the parts lift away and it starts again. A panel under the board tracks which parts are placed. The animation pauses off screen and shows the finished, powered board when reduced motion is on.
- DM Sans and DM Mono, with Noto Sans fallbacks for Russian, Chinese and Japanese that load only on those locales. Latin and Cyrillic fonts are self-hosted, so they load even when Google Fonts is unreachable.
- Studio on phones: the 3D view fills the screen, and the component library, schematic and inspector open as bottom sheets from a tab bar. Learn mode and Simulate are kept to larger screens.
- ESLint for the whole repo: arrow functions everywhere except Next.js layouts, React Hooks and Next.js rules, imports sorted by line length, and a British English spelling check on user-facing text and English messages.
- Missing-translation report (`pnpm --filter @echidna/web i18n:report`), also written to the GitHub Actions job summary.
- GitHub Actions CI: lint, typecheck, tests, build and the translation report for the web app; formatting, Clippy and tests for the Rust crates.
- Rust toolchain pinned to 1.98.0.
- DC operating-point solver in Rust (modified nodal analysis with Newton–Raphson) for resistors, capacitors, inductors, sources, diodes and a behavioural linear regulator with dropout, compiled to WebAssembly and run in a Web Worker.
- Component library: ground, 5 V supply, 150 Ω resistor, 10 µF ceramic capacitor, red 5 mm LED and a 3.3 V LDO, each with a JSON Schema-checked spec and value provenance.
- Rule engine with default voltage, current and power rating rules: warn above 80 % of a rating, fail above 100 %, and mark verdicts as estimated when they rest on estimated values.
- Schematic editor: place parts by dragging or clicking, wire pin to pin, move, rotate (R), nudge with the arrow keys, delete, pan, zoom and double-click to fit. Parts are outlined by verdict, wires show their net voltage, and the drawing scales with its panel.
- Live simulation: every edit is solved and checked straight away, with the solve time in the validator. Simulate pauses and resumes it.
- Inspector: editable values in the user's locale (including `4k7`-style notation), provenance badges, live voltages, currents and power, rating meters with Learn mode explanations, and pre-checked swap suggestions. Selecting a wire shows its net.
- "Open the 3.3 V regulator example" on the empty schematic.
- 3D board: a 100 × 70 mm board with black solder mask, gold pads, solder joints, silkscreen designators and mounting holes, and generic parts sized from their packages: resistor colour bands follow the value, the regulator shows its output voltage and the LED glows with its simulated current. Parts drag with 0.5 mm snap, and selection and verdicts are outlined on the board.
- 3D camera toolbar: zoom, fit board, 3D and top views, with keyboard shortcuts (+, −, F, T, Home, arrow keys to pan) and smooth transitions. Fitting shows the whole board on tall screens such as phones.
- Through-hole parts sit in drilled, plated holes, with copper rings on both faces and solder joints on the underside. The holes move with the part.
- The 3D board is routed automatically: copper tracks follow the wiring on both layers at 45°, with tented vias where a track changes layer and wider tracks for supply and ground. The routing is a preview, not checked for manufacture.
- The 3D board has fiducials, a "REV A" legend with the project name, and a choice of black, green, blue or red solder mask, remembered per user.
- Underside view (B) in the 3D toolbar; the camera can now orbit beneath the board to the solder side.
- Collapsible component categories in the library, remembered per user and opened while searching.
- Golden DC circuits in `tools/golden`, compared against ngspice in CI to within 0.1 %.
- Solver models for NPN and PNP bipolar transistors (Ebers–Moll with Early effect) and n- and p-channel MOSFETs (SPICE level 1), with SPICE-style voltage limiting, and six transistor golden circuits.
- LEDs are one generic 5 mm part with a colour chosen in the inspector: red, yellow, green, blue or white, each with its own forward voltage. Saved projects with the old red LED open as a red LED.
- A lit LED glows in its own colour, with brightness that follows the simulated current, and goes dark when its circuit is open. An unlit LED's epoxy is a dark tint, so it no longer passes for lit.
- The inspector says whether a selected LED is lit, and when it is dark, why: a lead is unwired, both leads are on the same net, it is wired backwards, or the loop is not closed. A current rating with no current through it reads "No current flowing" instead of "Within rating".
- A slide switch (SPST, 0.5 A) with an on/off position chosen in the inspector; its schematic symbol and 3D actuator follow the position. The solver has a switch element for it: closed, it conducts through its 30 mΩ contact resistance; open, it is an ideal break and carries exactly no current. The example circuit now runs the supply through it, switched on, so the LED lights as soon as the example loads.
- The board can be resized from the inspector, from 40 × 30 mm to 200 × 200 mm. Parts left outside a smaller board move in to its edge, and the camera reframes the new outline.
- Transistor parts: 2N3904 (NPN), 2N3906 (PNP), 2N7000 (n-channel MOSFET) and BS250 (p-channel MOSFET, all values estimated), with schematic symbols, TO-92 footprints and 3D packages marked with the part number.
- Playwright end-to-end test of the Phase 1 acceptance scenario in English and French, checking the warning and fail appear within 100 ms.
- CI builds the WebAssembly solver (with a `wasm-bindgen` CLI matching `Cargo.lock`), runs the end-to-end tests and runs the golden circuits against ngspice.
- Transient analysis in the solver (`solveTransient` in WebAssembly): simulates a circuit from switch-on, with capacitors discharged and inductors carrying no current, in equal steps using backward Euler for the first and Gear 2 after. It returns node voltages, pin currents and power over time. Six golden transient circuits (RC charge, RL rise, ringing RLC, an LED switching on as a capacitor charges, a regulator feeding an RC filter, and an NPN turned on through a base RC delay) match ngspice within 1 %.
- "After switch-on" in the inspector: plots of the selected part's voltage and current from the moment the circuit is switched on. The run length is chosen automatically, from 10 µs up to 10 s, to frame the circuit settling, and is re-run on every edit in a separate worker after the verdicts are out. Pointing at the plots, or focusing them and using the arrow keys, replays switch-on on the 3D board, with LEDs glowing at the current of that moment. A circuit that stores no energy says it reaches its values at once, and one that cannot be simulated says so.
- Switch-on checks in the validator, configured in `rules.json` alongside the DC rules: voltage overshoot against a part's voltage rating, and current and heat against its ratings averaged over the worst millisecond, so a large capacitor that overloads a regulator or switch while it charges is flagged even though the settled circuit passes. Averaging ignores the instant, step-sized spike an ideal supply drives into a decoupling capacitor. They add warnings and fails only, after the DC verdicts.
- Temperature estimates: each resistor, LED, regulator and transistor now carries a thermal resistance to the surrounding air and a maximum temperature, with provenance. The inspector shows its estimated temperature in °C, and a temperature check warns from 80 % and fails above 100 % of the rise the part can take above the air, so a part that is within its power rating can still warn in hot surroundings. The air temperature is set under Surroundings in the inspector (25 °C by default, −40 to 85 °C) and saved with the project. A temperature estimate that rests on an estimated thermal resistance is flagged as estimated without softening the part’s other verdicts.
- Push button (SPST, normally open, 50 mA at 24 V) in the library, with its own schematic symbol, footprint and 3D model whose plunger sinks while pressed. In the inspector it is pressed by holding a button, with the pointer, Space or Enter, and springs back when let go; a project is never saved with it held.
- Switches are operated the way the real part is: latching switches such as the slide switch flip with a toggle in the inspector, and momentary ones such as the push button with a button. Each part declares which it is (`actuation` in its spec).
- Current and heat overlays on the 3D board, switched on from the view’s toolbar and remembered per user. Current shows as dashes running along the copper in the direction current flows, faster for more current, worked out for every track from the solved pin currents; it follows the switch-on playback while scrubbing. Heat shows as a glow on the board around each part, coloured by its estimated temperature on a fixed scale from 25 °C to 150 °C and stronger the more the part warms above the air. A legend explains whichever overlays are on. With reduced motion the dashes stand still, their bright heads still pointing the way current flows.
- Dev boards and slots: Raspberry Pi 4 Model B, Raspberry Pi 5, ESP32-DevKitC and Arduino UNO R4 Minima as host boards, each with supply rails and an I²C header and GPIO pins to plug parts into. A project can start from any of them from the empty schematic. Each rail's voltage and current limit carries its provenance; limits the makers don't publish are estimates.
- Sensors that plug into a dev board's slots: BME280 (temperature, humidity and pressure over I²C), HC-SR04 ultrasonic distance sensor and DS18B20 (temperature over 1-Wire), each with its supply range, current draw and signal levels from its datasheet.
- Slot checks (`checkSlotFit` in `@echidna/rules`): before a part goes in a slot it must pass the protocol check, a supply check that the slot offers a rail in the part's range, a rail current budget counting everything already plugged in, signal levels both ways (the part's outputs into the board's pins, and the board's into the part's), and the slot's thermal budget when it has one. Thresholds live in `rules.json`.
- The inspector lists every slot a selected sensor could go in, each already checked: slots that fit say which rail would power it and can be plugged into in one click, which wires the supply, ground and signals; slots that fail say why, for example that an HC-SR04's 5 V echo would exceed a Raspberry Pi's 3.3 V pins, and cannot be chosen. A dev board's inspector shows the current drawn from each rail and what is in each slot.
- Swaps that keep parts plugged in: the inspector of a plugged-in sensor lists the other sensors that could take its slot, and a dev board's lists the other boards that could take everything plugged into it, each checked before it is offered. A swap that fits keeps every part in its slot with its wiring; one that doesn't says which part it would fail and why, for example that an Arduino UNO R4's 5 V I²C would overdrive a BME280, and cannot be applied.
- Desktop builds: a motherboard is a host whose slots (CPU socket, cooler mount, PCIe x16, memory, M.2 and ATX power) take modules: CPUs, graphics cards, memory, SSDs, coolers and PSUs. 21 parts with their power draw, cooling rating, PSU output and connectors, each with provenance; figures makers don't publish, such as board power and cooler ratings, are estimates.
- Module checks (`checkModuleFit` and `checkBuild` in `@echidna/rules`): the build's full-load draw against the PSU's rated output (warn at 80 %, fail above 100 %), the PSU's 24-pin, EPS, 8-pin PCIe and 12V-2x6 connectors against what the motherboard and cards need, and the CPU's package power against the cooler's rating (warn at 90 %). Thresholds live in `rules.json`. Desktop modules are checked as a build, not solved as a circuit.
- Budget, gaming and workstation reference desktops to start from the empty schematic, with every module plugged in. A plugged-in module is offered only the slots that take it and swaps for others in the same role, each checked first: swapping the budget build's RTX 4060 for an RTX 4090 is refused with "634 W of 550 W" and the missing 12V-2x6 connector. The motherboard's inspector lists the power and cooling checks, and they appear in the validator on the PSU and cooler.
- Laptops: an ultrabook and a gaming laptop to start from the empty schematic. Their boards have the processors (and, on the ultrabook, the memory) soldered on, and slots for SO-DIMM memory, an M.2 SSD, an M.2 E-key Wi-Fi card, a 3- or 4-cell battery, an eDP display, a cooler and a USB-C or barrel charger. 22 laptop parts, each value with provenance.
- Laptop checks: the charger's output against the laptop's full-load draw (warns from 100 %, as the battery makes up the difference for a while, and fails above 150 %), and the cooler against the heat of the soldered-on processors. The board's inspector estimates time on battery in light use from the battery's energy and each part's light-use draw. Swaps only offer parts made for the same kind of device, so a desktop PSU is never offered for a laptop.
- Dev boards and sensors draw as boxed schematic symbols with a lead per pin, and as pin headers on the board.
- Every project is built on the right foundation. Circuits, sensors and dev boards go on a bare PCB; a desktop build goes in a desktop case and a laptop build in a laptop chassis, with no copper, drill holes, fiducials or board legend. The first part into an empty project sets the foundation, and the library then greys out parts that belong elsewhere and says why, such as "Goes in a laptop chassis. Start a laptop build to use it." A chassis's size is fixed, and saved builds move off the PCB they were on.
- Desktop and laptop builds at life size: an ATX board on the tray of a mid-tower laid on its side, with the PSU in the shroud below, and a laptop's mainboard in its bottom shell with the battery under the palm rest and the display in the open lid. Each module sits in its slot's seat on the board (`seat` in a host slot's spec), moves with the board when it is dragged, and is drawn in a material that suits it.
- Drones: DJI Mini 2, Mini 3 Pro and Mini 4 Pro presets and a generic 5-inch FPV quad, on a round landing pad. A drone's frame is its host, with slots for motors, propellers, battery, camera and, on the FPV frame, a 4-in-1 ESC and flight controller (the DJI Minis have theirs built in). Twenty-seven parts, each value tagged with its provenance: masses, capacities and energies from DJI's specifications, the rest estimated with a stated reason.
- Drone checks (`checkDrone`, thresholds in `rules.json` `drone`): thrust to weight (warn when the drone weighs half the motors' full thrust, fail above 80 %), each motor's full-throttle current against its ESC's continuous rating, and the motors' total current against the battery's capacity times its C-rating. Swaps are checked first, so an under-rated ESC is refused with both currents shown.
- Hover time (`flightTime`): momentum-theory rotor power, √(T³ / 2ρA), over the motors' hover efficiency, plus what the electronics draw, from the battery's energy. Shown on the frame beside the maker's figure while the drone is as it ships. Each DJI preset is within the stated 10 % of its published flight time (31, 34 and 34 minutes), as are the Mini 3 Pro and Mini 4 Pro with the Battery Plus (47 and 45 minutes), which the model was not tuned to.
- 3D drones drawn to each family's layout: a moulded body or carbon plates on standoffs, arms out to the motor mounts, motors and two- or three-blade propellers on every arm.
- Phones and wearables: iPhone 13 to 17, iPhone 18 Pro and Pro Max, Galaxy S21 to S26, a generic smartwatch and a generic fitness band, laid out on a repair mat as in a teardown. A logic board is the host, with slots for the SoC, modem, PMIC, battery, display, rear camera and charging coil, or a wearable's sensors, haptics and radio. 102 parts, each value tagged with its provenance: battery capacities from teardowns, regulatory filings and Samsung's specifications, the rest estimated with a stated reason.
- Stacked boards: a host can be made of several boards (`host.boards`), stacked on an interposer like an iPhone's sandwich or joined by a flex cable like a Galaxy's sub-board. Each slot says which board it is on, or that its part sits away from the board on a flex cable, and the 3D view draws the stack and the cables.
- PMIC rail budgets (`checkPhone`, thresholds in `rules.json` `phone`): what every part on each PMIC rail draws at peak against what the rail supplies. A swap is checked against the rail it draws from, or every rail for a PMIC. Device-specific connectors (`Interface.connector`) keep one phone's display or battery out of another, and parts made for another phone are not offered as swaps.
- Battery life for phones and wearables, shown on the logic board beside the maker's figure while the phone is as it ships. Each iPhone preset is within the stated 10 % of Apple's video playback figure; the draws behind the estimate are estimates fitted to those figures, so this guards against drift rather than validating them.
- Every desktop, laptop, drone, phone and wearable part now lists its figures in the inspector, each with its provenance badge; hovering a badge shows its source or the reasoning behind an estimate.
- A fail that rests only on estimates is worded as likely everywhere it is shown: "Probably can't plug in here", "Probably wouldn't fit", and "Likely: …" in a build's checks.
- The ready-made builds offered on an empty schematic are grouped by device.
- Export from the studio's top bar. A bare board downloads as one zip ready for a board house: two-layer Gerbers (RS-274X with X2 attributes: copper, solder mask, paste, silkscreen with designators, outline), an Excellon drill file, a bill of materials and a pick-and-place file, all in millimetres from the board's bottom-left corner. A desktop, laptop, drone, phone or wearable build downloads its bill of materials. A README in the zip lists any connection the router couldn't finish, and the studio says so after exporting.
- A ground pour on both copper layers of an exported board: every part of the board 0.3 mm clear of other nets' copper is ground, ground pads join it through four-spoke thermal reliefs, and copper with no path to ground, such as the slivers beyond the mounting holes, is removed.
- Part numbers in the bill of materials (`sourcing` on a part: maker, part number and LCSC number), for the parts whose numbers have been checked against a distributor: the ceramic capacitor, the AMS1117 regulator, the 2N7000, 2N3904 and 2N3906, and the supply's screw terminal. A resistor's number is made from its value in YAGEO's CFR code (`150R`, `4K7`), for E24 values only; a part whose value has been changed loses its fixed number.
- Populated boards in 3D: every motherboard, laptop board, and phone's and wearable's board stack carries the small parts a real one does (0201–0805 resistors and capacitors, small ICs and BGAs with their decoupling, power inductors, a crystal, test points, and a ring of power stages round the CPU or SoC), from about 80 on a fitness band to over 1,000 on a desktop board. They are fixed decoration, laid out the same way every time, kept clear of every slot's seat and drawn instanced, one draw call per material.
- Modules in their real form rather than plain blocks: a graphics card's shroud, three fans, PCIe fingers and bracket; a tower cooler's copper heat pipes, fin stack and fan; an AIO pump head; a PSU's fan grille and label; DIMMs under heat spreaders; an SO-DIMM's memory chips; an M.2 drive's controller, DRAM and NAND; a CPU's heat spreader; a laptop's heat pipes, blowers and fin stacks, battery cells and display glass; a Wi-Fi card's shield can; a drone's ESC and flight controller as populated boards; phone and wearable chips as BGA packages; and a charging coil's copper turns.
- AC small-signal analysis (`solve_ac` / `solveAc`): a SPICE-style `.ac dec` sweep with one source driven at 1 V or 1 A, linearising diodes, transistors and regulators at the DC operating point. Available from the solver worker as `ac`, with golden RC, RLC, BJT and MOSFET amplifier and regulator circuits checked against ngspice in CI.
- `GET /api/v1/healthz`, a Next.js route handler reporting the app as healthy, uncached.
- Link previews and icons: every page has a canonical URL, language alternates, Open Graph and X (Twitter) cards with the home page hero as the image (alt text in each language), and the Echidna favicon. The site URL defaults to `https://echidna-one.vercel.app` and can be set with `NEXT_PUBLIC_SITE_URL`.

### Changed

- A part drawn as a box in the schematic, such as a module or host board, is sized by its real size on a compressed (logarithmic) scale: a 3 mm IMU draws small and a 305 mm motherboard large, both still legible. A loaded build lays its modules out in columns about as tall as the host's box, so the view fits it.

- The 3D board's copper is routed properly. Each connection is found by a path search on both layers that keeps 0.25 mm clear of every other net's pads, tracks and vias, of the mounting holes and fiducials, and of the board edge, so tracks no longer cross other nets, run between a regulator's pins or drop a via onto another net's pad. Pads of the same pin, such as a regulator's tab and middle lead, are no longer joined by a track. A connection with no clear path shows as a dashed yellow line instead of copper. While a part is dragged the copper waits, and re-routes when it is dropped.
- Solder mask keeps its colour from every angle: a black board reads black and a green one green, where the studio lighting had washed them out to grey and sage.
- Copper tracks are a darker shade of the board's colour, with a soft neon glow in a bright shade of it along their edges, on both faces. The glow follows the mask colour.
- A faint dotted line no longer crosses the board: the key light's shadow map now reaches well past the board's edges.

- Verdicts appear about 40 ms sooner after editing a part’s value: the 3D board no longer re-routes its copper and re-cuts every drilled hole when only a value or variant changes, which held up the solver’s reply on the main thread.
- The 3D board redraws only when something changes, instead of 60 times a second, so an idle studio uses no GPU time. It still animates every frame while the current overlay is on.
- The selected solder-mask colour and the overlays that are switched on are now highlighted in the 3D toolbar.
- The "Try a swap" demo moved from the hero to its own section below it.
- Starting from a desktop or laptop build fits the whole build in the schematic view. The view was fitted to wire pins, which modules don't have, so a build stayed at the default view with its last parts out of sight.
- The cooling check reads "Up to 170 W of heat to remove" rather than naming the CPU, as a laptop's cooler takes the graphics' heat too, and the rule is now called "Cooling".
- An unpowered linear regulator now turns off: its output disconnects and its bias current falls with the input, instead of forcing its full quiescent current through whatever feeds it (which drove the input of a regulator behind an open switch to about −500 kV).
- A regulator whose supply sags under a heavy load now settles in dropout instead of failing to converge. The solver moves it one mode at a time (regulating, dropout, off), so it no longer flips between regulating and off; this happened when a capacitor across an LED's resistor drew a large current at switch-on.
- Pins wired to different ground symbols are now joined by copper on the 3D board, as they already were in the simulation, so every wired pin of a part gets its track instead of only the one not going to ground.
- New parts land on the board where their footprint clears every placed part, the board edge and the mounting holes, instead of on a fixed grid.
- Readouts show leftover leakage below a picoamp as zero, and unitless values such as current gain without an SI prefix.
- Token font stacks now read `--font-*` variables first, so the app can supply self-hosted fonts.

### Removed

- The separate Rust / axum API service (`services/api`, `echidna-api`). The API is Next.js route handlers in the web app, so Echidna deploys as one unit.
